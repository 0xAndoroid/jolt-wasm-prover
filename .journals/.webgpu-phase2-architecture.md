Donors audited read-only: Metal `gpu/metal-backend`@ef53a2c67 (worktree gpu-metal-backend), CUDA parity pin 98a6f3eba (+ structural pointers from `.metal-m5-cuda-port-audit.md` @f791ba59d), June WebGPU `jolt-wasm-prover@webgpu-e2e-bench` (4ba6cf4), target tree `perf/manycore-scaling`@70a294ad5 (worktree perf-manycore). ## 0. Premise and win model

**Go is already decided at the primitive level.** W1d measured BN254 mont-mul through Tint on this M4: **0.928 Gmul/s (16-bit CIOS; 13-bit falsified at 0.60 — all widths hit the same ~490 G mul32/s roof, carries are free on M4, mul count is the cost)**. That is 1.57× CPU-native-all-core (0.59), **~2× CPU-WASM (~0.46)**, 0.56× Metal-native (1.65). June's 27× browser loss is **re-attributed**: their kernel ran AT the roof under Tint — the gap was big-kernel composition (register pressure/occupancy) + orchestration/readbacks, not the primitive and not "Tint codegen" per se. Internal precedent (user): a WebGPU prover beating CPU-WASM exists, with its gains in **commitment + opening** stages. The remaining falsifiable hypothesis is **composition**: does a full EC point-op kernel hold ~0.9 Gmul/s under Tint? Wave 1 is built as that falsification instrument.

**Win model @2^20–2^22 (canonical 2^22), Chrome on M4 mini (10-core GPU, 16GB, 96GB/s):**
- Roofline verdict (M4, @2^23 shape): st0 commit + st8 opening = EC-ALU-bound, **49% of stage wall**, the only pools with real arithmetic to steal; st1–7 latency/serial-bound; nothing DRAM-bound on CPU.
- W1d economics: **ALU-dense work (EC point adds, batched inverse, pairing towers, MSM buckets) beats CPU-WASM ~2–3×; DRAM-streaming folds do NOT (0.40 Gmul/s at the shared 97GB/s bus)** — unless CPU-WASM can't saturate the bus (open; measured in W2).
- Amdahl: EC lanes alone (st0+st8 ≈ 50% of wall at 2–3×) ≈ 1.35–1.5× whole-prove; overlap (GPU commit under CPU witness stream — Metal W3a shape, free in practice) + sumcheck second front + CPU-side X21 port push to the **campaign target ≥1.5–2× vs CPU-WASM**. Metal analogue: 2.25× native at 1.65 Gmul/s; we have 0.93 → 2× vs CPU-WASM is the honest class, not 5×.

## 3. Backend seam plan (target tree)

The seam is **`crates/jolt-kernels/src/backend.rs`**: `JoltBackend<F, PCS>` = 35-slot registry — `commit: Box<dyn CommitWitness<F,PCS>>`, 2 uniskip fronts (`UniskipKernel`), ~30 `Box<dyn PrepareKernel<F, R>>` sumcheck slots (one per relation type, `#[derive(KernelSlots)]` maps relation→slot), `advice_opening`, `joint_opening: Box<dyn JointOpeningPolynomials<F>>`. `PrepareKernel::prepare(&self, session: &mut ProofSession, witness: &dyn JoltWitnessPlane<F>, inputs) -> Box<dyn SumcheckKernel>`. **`ProofSession`** = TypeId-keyed Any map with `park`/`take` cross-stage carries — device-buffer residency lives here exactly as Metal uses it. Spec: `specs/clean-slate-prover.md` "The backend seam".

**`webgpu/` arm mirrors `metal/` exactly:**

```rust
// crates/jolt-kernels/src/webgpu/mod.rs
pub fn webgpu(opts: WebGpuOptions) -> Result<Self, WebGpuError> {   // Fr-concrete, like metal()
    let ctx = WebGpuContext::global(opts)?;      // fail-closed: adapter/device/pipeline errors HERE, never mid-proof
    let mut backend = Self::optimized();
    backend.commit = webgpu_dory_commit_slot()…; // wave 1
    backend.joint_opening = Box::new(WebGpuJointOpening { fallback: OptimizedBackend }); // wave 2
    // …per-wave slot installs, each { fallback: optimized twin } + min-terms gate
}
```

- **Gating:** native = `JOLT_WEBGPU_DISABLE`, `JOLT_WEBGPU_MIN_TERMS[_<SLOT>]` (Metal's exact machinery). wasm32 has no env: `WebGpuOptions { disable, min_terms: HashMap<SlotId, usize>, … }` constructed from JS; env-var path delegates to the same struct so both targets share one gate implementation. Every landed slot extends the forced-env byte-parity list (CUDA runs 14 forced envs — same discipline).
- **CPU fallback / incremental landing:** every slot holds its optimized twin; below threshold, device-init failure, or unsupported geometry → soft-decline to twin. Proof bytes must be identical either way ⇒ **byte_diff gate per slot** (jolt-kernels Rust tests, Metal's 19/19 pattern): prove with optimized arm, prove with webgpu arm, compare proof bytes; forced-engagement env sweep.
- **Two test tiers (the naga-vs-Tint divergence is a feature here):**
  1. *Correctness*: `cargo nextest` native via wgpu/naga (June dory-gpu's 33-test pattern: field/curve/fold/msm/pairing/e2e). Values are compiler-independent; keep kernels small (≤5 inlined point-ops — naga loop-bounding hang AND Tint/AIR compile blowup share the fix).
  2. *Performance + Tint truth*: node-webgpu (≡ Chrome bitwise) via `wgsl-bench/` (p2/wgsl-microbench branch) per-kernel regression + Playwright/Chrome e2e with persistent profile (Dawn blob cache kills the 10-min cold compile from run 2). **No kernel perf decision off naga numbers, ever.**
- **Engine / threading:**
  - *Native*: `WebGpuContext` owns Device+Queue (wgpu); submission from slot code directly; engine-side CPU work on a **private rayon pool** (June's deadlock fix: never inject into the parked global pool).
  - *Browser*: prover runs in a dedicated worker (wasm-bindgen-rayon pool per W1a's port). **June's engine skeleton survives** (`june:context.rs`, `par.rs`, gpu-pcs glue): dedicated GPU worker owns the Device and keeps its JS event loop live; prover thread enqueues a job into the SAB queue and blocks on `Atomics.wait`; GPU worker submits, `onSubmittedWorkDone` → writes results → `Atomics.notify`. Two changes vs June: (a) **job granularity = PHASE, not op** — a job is "encode these N dispatches, one submit, at most one readback"; the 5–15ms floor is paid once per phase, ~1µs/dispatch inside; (b) GPU jobs are issued only from the stage-driver thread (slot `prepare`/`collect`), never inside `par_iter` — wasm serial fallbacks for engine-side loops (June's fix, port as-is).
  - *Round-serial sumchecks/reduce rounds*: never mapAsync per round. Options in priority order: batch rounds device-side with max-rounds indirect encoding (r1#2); CUDA early-handoff (device for big rounds, one readback, CPU tail); accept per-round submit (0.2ms) but never per-round readback. Dory reduce (~13 rounds @2^22): v1 = per-round message readback ≈ 13×5–15ms ≈ 0.07–0.2s — acceptable against a multi-second pool; v2 = on-device transcript absorb (Blake2b WGSL) to eliminate readbacks — open question, don't commit.
- **Residency map (`WebGpuSession` in ProofSession, all outside the 4GB wasm heap):** one-hot Ra index streams + tier-1 grid (st0), dense Inc rows, v1/v2 reduce vectors + row set (st8), shared eq tables, later resident record columns. @2^22 ballpark: record ~0.5GiB, tier-1 grid ≤2GiB, st8 row set ~0.25GiB — comfortably inside 4GiB−4/buffer and the mini's 16GB (co-run budget with 4GB wasm heap + Chrome ≈ 8–10GiB device — fine; 2^23+ needs the small-space/streaming levers — future, not designed for now).
