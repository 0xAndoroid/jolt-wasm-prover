# WebGPU/WGSL engineering survey — research lane r1 (2026-07-30)

Scope: general WebGPU/WGSL crypto/bignum engineering literature to feed Jolt WebGPU backend kernel design. Target: Apple M4, Chrome/Dawn/Tint→MSL primary. Per directive, no hunt for other Jolt-on-WebGPU work.

Kernel families referenced: **F1** BN254 Montgomery mul · **F2** Pippenger MSM · **F3** one-hot/gather commitments · **F4** sumcheck fold/eval · **F5** batch inversion · **F6** Miller-loop micro-op mega-dispatch.

---

## Ranked ideas

### 1. 13-bit reduced-radix lazy-carry Montgomery limbs (F1 → everything)
- **Idea:** 20×13-bit limbs in u32, defer carries across ~32 accumulated partial products (headroom k = 2^(32−2W); W=13 → 64), propagate once. Replaces 16×16→32 eager-carry CIOS.
- **Est. gain:** ZPrize 2023 winner (Tal Derei + Koh Wei Jie) measured Montgomery-mul batch: 13-bit **88ms vs 16-bit CIOS 366ms on M3 (4.2×)**, 129 vs 645ms on M1 (5×). Mechanism confirmed by Apple ALU throughput (metal-benchmarks): IMUL32 = 4 cyc but **RSHIFT32 ≈ 8 cyc** — a carry (shift+mask+adds ≈ 11 cyc) costs ~2.7 multiplies, so carries dominate, not muls. 13-bit does MORE muls (820 vs 528 per 256-bit mul) and still wins on carry elimination + ILP (eager carries serialize the dependency chain).
- **Cost:** rewrite of the field core + all constants in 13-bit Montgomery form; conversion kernels at buffer boundaries. ~Days, contained.
- **Risk:** low — cross-vendor evidence; 13/14 crossover may shift on M4 (15-bit won on NVIDIA; Apple-only regression risk if we ever target other GPUs → keep limb width a compile-time parameter).
- **Evidence:** [ZPrize 2023 entry](https://github.com/z-prize/2023-entries/tree/main/prize-2-msm-wasm/webgpu-only/tal-derei-koh-wei-jie), [HackMD write-up](https://hackmd.io/HNH0DcSqSka4hAaIfJNHEA), [twisted-edwards repo](https://github.com/td-kwj-zp2023/webgpu-msm-twisted-edwards), [Penumbra blog](https://www.penumbra.zone/blog/accelerating-client-side-cryptography-with-webgpu), [mitschabaude/montgomery](https://github.com/mitschabaude/montgomery) (lineage), [philipturner/metal-benchmarks](https://github.com/philipturner/metal-benchmarks), [ICME-Lab/msm-webgpu](https://github.com/ICME-Lab/msm-webgpu) (BN254, closest prior art).

### 2. Single-encoder max-rounds encoding + indirect dispatch; never read back per round (F4, F2, engine)
- **Idea:** batch ALL dispatches of a phase into one command encoder / one `queue.submit()`; for variable trip counts, encode max rounds up front with `dispatchWorkgroupsIndirect` whose counts a GPU kernel writes (zeroing dead rounds). No per-round mapAsync.
- **Est. gain:** Chrome mapAsync round-trip is **5–15ms flat, size-independent** ([gpuweb#4432](https://github.com/gpuweb/gpuweb/issues/4432), [crbug 41487454](https://issues.chromium.org/issues/41487454)); ~25 sumcheck rounds × 5ms = **125ms of pure latency** if orchestrated naively — potentially bigger than any kernel win. Per-dispatch API overhead in Chrome 32–59µs when submitted separately, ~5µs encoded inside one submit; submit itself is ~40% of overhead ([arXiv 2604.02344](https://arxiv.org/abs/2604.02344)).
- **Cost:** engine-level design constraint (this shapes the job-queue architecture); moderate.
- **Risk:** low. Indirect-args validation dispatches on D3D12 pollute timestamps; Metal backend cheap. Cannot write+consume indirect buffer in the same pass (earlier-pass-writes/later-pass-consumes in one command buffer is legal and is the pattern).
- **Evidence:** links above + [toji.dev best practices](https://toji.dev/webgpu-best-practices/), [gpuweb CommandSubmission design doc](https://github.com/gpuweb/gpuweb/blob/main/design/CommandSubmission.md).

### 3. dawn-gpu/node-webgpu as primary native/CI harness (all families)
- **Idea:** run the SAME WGSL natively under Dawn/Tint via npm [`webgpu`](https://www.npmjs.com/package/webgpu) ([dawn-gpu/node-webgpu](https://github.com/dawn-gpu/node-webgpu), maintained, macOS-arm prebuilts, exposes Dawn toggles) instead of wgpu/naga.
- **Est. gain:** correctness of conclusions, not runtime: it exercises **Tint→MSL + Dawn Metal — the exact Chrome compiler path** — and sidesteps our known naga loop-bounding Metal hang. Deno/wgpu = naga (Firefox stack), demonstrably different perf profile: Safari 31.7µs vs wgpu-native 71.1µs per dispatch on identical M2 ([arXiv 2604.02344](https://arxiv.org/abs/2604.02344)).
- **Cost:** low — node harness alongside existing bench.mjs.
- **Risk:** low; keep Playwright/Chrome as end-to-end ground truth (browser IPC/submit/mapAsync costs only exist there), keep wgpu/naga as secondary portability check but never let naga gate Metal kernel decisions.
- **Evidence:** [Dawn node README](https://dawn.googlesource.com/dawn/+/HEAD/src/dawn/node/README.md), [deno_webgpu = wgpu/naga](https://crates.io/crates/deno_webgpu).

### 4. Bench flags: disable robustness + workgroup zero-init, unquantized timestamps (all)
- **Idea:** Playwright launch args `--enable-dawn-features=disable_robustness,disable_workgroup_init --enable-webgpu-developer-features`; time kernels with compute-pass `timestampWrites` (quantization off with dev-features flag; default is 100µs quantization).
- **Est. gain:** robustness cost measured 17–30% on ML compute ([gpuweb#1202](https://github.com/gpuweb/gpuweb/issues/1202)); Web Stable Diffusion claims ~3× on their workload ([websd.mlc.ai](https://websd.mlc.ai/)). Workgroup-array clamping is the heaviest case. Report flagged AND unflagged: the delta is the un-shippable "cost of the web platform" line item — users run default Chrome.
- **Cost:** trivial.
- **Risk:** none for benching; note Chrome ≥141 integer-range analysis elides clamps it can prove ([crbug 348701956](https://issues.chromium.org/issues/348701956)) — masking indices (`idx & (N-1)`) and const indices into fixed arrays help the analyzer, shrinking the unflagged penalty for free. Headless-macOS trap: verify `adapter.info` shows Metal, not fallback ([toji/webgpu-test](https://github.com/toji/webgpu-test) reports ~25× software path); run headed if so.
- **Evidence:** [Dawn Toggles.cpp](https://github.com/google/dawn/blob/main/src/dawn/native/Toggles.cpp), [Dawn debugging.md](https://dawn.googlesource.com/dawn/+/refs/heads/main/docs/dawn/debugging.md), [Chrome WebGPU dev features](https://developer.chrome.com/docs/web-platform/webgpu/developer-features), [Chrome 121 timestamp-query ship](https://developer.chrome.com/blog/new-in-webgpu-121).

### 5. Subgroup ops for register-resident reductions (F4, F2 bucket accumulation)
- **Idea:** `enable subgroups;` — subgroupAdd/Shuffle/Broadcast/Ballot etc. Shipped Chrome 134 stable; Apple subgroup size is exactly 32 (min=max, hardcoded in [Dawn PhysicalDeviceMTL.mm](https://github.com/google/dawn/blob/main/src/dawn/native/metal/PhysicalDeviceMTL.mm)); `subgroup_id`/`num_subgroups` since Chrome 144; `subgroup_uniformity` relaxation since 145.
- **Est. gain:** measured on this M4 (agent bench, headless Chrome 149, timestamp queries): register-only reduction **5.3× vs shared-memory tree** (10.34→1.95ms); memory-bound reduction **~0** (both saturate ~115GB/s). So: wins for ALU-resident partials in fold/eval and bucket pre-reduction (replacing atomics — 3DGS paper got 3.05× replacing atomicAdd with quad pre-reduce, [arXiv 2505.18764](https://arxiv.org/pdf/2505.18764)); no win where DRAM-bound.
- **Cost:** low-moderate; kernels can assume width 32 on Apple but must not hardcode it portably.
- **Risk:** low; subgroup builtins need uniform control flow (diagnostic relaxable).
- **Evidence:** [Chrome 134 notes](https://developer.chrome.com/blog/new-in-webgpu-134), [subgroups proposal](https://github.com/gpuweb/gpuweb/blob/main/proposals/subgroups.md).

### 6. Full-tier limits: 4GiB buffers, 1024 invocations, 32KB shared, 10 storage bindings (F3, F2, engine)
- **Idea/finding:** measured live on this M4 (Chrome for Testing 149): maxBufferSize = maxStorageBufferBindingSize = **4GiB−4**; maxComputeInvocationsPerWorkgroup **1024**; maxComputeWorkgroupStorageSize **32768**; maxStorageBuffersPerShaderStage **10**; maxComputeWorkgroupsPerDimension 65535. All grantable via `requiredLimits`; **18GiB of live storage buffers allocated on the 32GB M4 without error** (unified memory). 4GiB−4 cap is hard: Dawn passes buffer sizes to MSL as u32 ([Limits.cpp](https://github.com/google/dawn/blob/main/src/dawn/native/Limits.cpp) tiering, [BufferMTL.mm](https://github.com/google/dawn/blob/main/src/dawn/native/metal/BufferMTL.mm)).
- **Implication:** witness/trace-scale data fits in browser device buffers; but any single binding >4GiB−4 must shard. >65535 workgroups → 2D dispatch or grid-stride. Probe scripts kept at `/tmp/probe3.mjs`, `/tmp/sgbench.mjs`.

### 7. Pipeline caching + async creation to kill the 10-min first-compile (build/UX)
- **Idea:** `createComputePipelineAsync` everywhere; persistent Chrome profile (`launchPersistentContext` user-data-dir) so Dawn's BlobCache → Chrome GPU disk cache persists MSL compilation across runs; split mega-modules only to parallelize pipeline creation.
- **Est. gain:** run-2+ pipeline creation typically near-instant vs cold compile; Tint itself is much faster post-IR-rewrite ("up to 7×", [Chrome 141](https://developer.chrome.com/blog/new-in-webgpu-141)) — the dominant cold cost on Metal is Apple's MSL→AIR compile, which the blob cache also skips.
- **Risk:** Metal-backend cache coverage undocumented — measure run1 vs run2 pipeline-creation wall time to confirm.
- **Evidence:** [Chrome 117 notes](https://developer.chrome.com/blog/new-in-webgpu-117/), [issue 42250927](https://issues.chromium.org/issues/42250927).

### 8. Decoupled Fallback single-pass scan/reduce pattern (F4, if multi-dispatch reduction ladder shows up in profiles)
- **Idea:** vanilla decoupled-lookback is unsafe (no forward-progress guarantee on Metal); **Decoupled Fallback** (Thomas Smith, SPAA 2025) bounds the spin then redundantly recomputes the blocking tile — near-memcpy scan on M1 Max/M3 via Dawn. Reference WGSL: [b0nes164/GPUPrefixSums](https://github.com/b0nes164/GPUPrefixSums).
- **Est. gain:** collapses log-depth dispatch ladders to one dispatch for chained reductions; relevant only if idea #2's batching leaves reduction-ladder overhead visible.
- **Risk:** moderate — subtle; adopt the reference implementation, don't reinvent.
- **Evidence:** [SPAA 2025 paper](https://dl.acm.org/doi/10.1145/3694906.3743326), [Raph Levien prefix-sum post](https://raphlinus.github.io/gpu/2021/11/17/prefix-sum-portable.html).

### 9. WGSL codegen hygiene under Tint/MSL (F1, F6)
- Module-scope `const`/`private` arrays are materialized as per-call `thread`-address-space copies in MSL ([naga#1461](https://github.com/gfx-rs/naga/issues/1461)/[wgpu#4367](https://github.com/gfx-rs/wgpu/issues/4367)) — put lookup tables (Miller-loop micro-op tables, window tables) in uniform/storage buffers; keep per-thread limb state in explicit scalars/`vec4<u32>` so unrolled code stays in registers (dynamic indices into fixed arrays spill to thread memory).
- Tint does no optimization by design ([dawn-graphics thread](https://groups.google.com/g/dawn-graphics/c/bbCgIrYYdng)); Apple's Metal compiler unrolls aggressively → the naga large-kernel trap conceptually carries to Tint too (huge unrolled functions blow up the MSL→AIR compile). Keep kernel bodies bounded; the ≤5-point-op rule likely applies Chrome-side as well, verify.
- `workgroupBarrier` in non-uniform control flow = hard compile error; canonical escapes: hoist barrier out of branches, `workgroupUniformLoad` for one-thread-writes-flag loops.
- Occupancy: Apple register file ~208KB/core, 3072 threads/core max; FP32 throughput degrades 3.6× from max to min occupancy — register-heavy 20-limb kernels will trade occupancy; benchmark workgroup sizes 64–256, not 1024.

## Dead ends — do not spend time on

- **dot4U8Packed/dot4I8Packed for 8-bit limbs:** Metal has no DP4a; Tint and wgpu both polyfill to unpack+dot ([wgpu#7494](https://github.com/gfx-rs/wgpu/pull/7494)) → 4 muls+3 adds anyway, and 32 limbs → 1024 partial products. Strictly worse than 13-bit.
- **f16/f32 FMA limbs (Emmart-style):** needs f64 + guaranteed-fused single-rounding FMA. WGSL has no f64; `fma` accuracy "inherited from x*y+z"; **Dawn compiles all MSL with relaxed math** (`#pragma METAL fp math_mode(relaxed)`, ShaderModuleMTL.mm) — exact-rounding tricks unsound in Chrome-on-Metal. f16 mantissa (11 bits) useless for 256-bit.
- **Waiting for u64/umulExtended in WGSL:** [gpuweb#1565](https://github.com/gpuweb/gpuweb/issues/1565) open since 2021, parked "Milestone 4+", absent from recent WGSL agendas; [gpuweb#5152](https://github.com/gpuweb/gpuweb/issues/5152) (64-bit ints) open. Native 8-limb mulhi CIOS (~7.6× faster per [field-ops-benchmarks](https://github.com/moven0831/field-ops-benchmarks) Metal-vs-WebGPU on M3) stays unreachable.
- **Barrett over Montgomery:** no WGSL evidence Barrett wins; ZPrize winners kept Montgomery for the hot path, Barrett only for input conversion. (~85% confidence.)
- **Uber-kernel with grid-wide sync / vanilla decoupled-lookback / cross-workgroup job queues within a dispatch:** no forward-progress guarantee on Apple; WGSL atomics are relaxed-only, `storageBarrier` is workgroup-scope only ([PR#2297](https://github.com/gpuweb/gpuweb/pull/2297), [#2229](https://github.com/gpuweb/gpuweb/issues/2229)) — cross-workgroup message passing impossible beyond a single u32 atomic payload. Coordination = separate dispatches (implicit inter-dispatch barriers are guaranteed) or Decoupled Fallback.
- **16-bit muls to save ALU:** IMUL16 = IMUL32 = 4 cyc on Apple; no saving.
- **Subgroup matrix (cooperative matmul):** experimental-only (unsafe-APIs flag), float/int8-oriented; irrelevant to bignum.
- **Firefox as a bench target:** ~1040µs/dispatch (rate-limited) per [arXiv 2604.02344](https://arxiv.org/abs/2604.02344).

## Architecture-relevant facts (engine)

- Inter-dispatch storage coherence on one queue is guaranteed (implicit barriers) — job granularity = dispatch; build the queue engine on that boundary.
- mapAsync ≈ 5–15ms flat and `onSubmittedWorkDone` rides the same ms-scale IPC path — CPU-driven per-round loops are architecturally ruled out in the browser; micro-op-stream mega-dispatch (F6 plan) and max-rounds indirect encoding are the right shapes. Atomics.waitAsync+SAB doesn't shorten the GPU-process round-trip; a dedicated GPU worker only frees the main thread.
- Chrome-vs-native overhead deltas (per-dispatch ~30–60µs vs ~24µs; submit-dominated) are the only systematic difference between the node-webgpu harness and browser — measure them once, then trust the harness for kernel-level decisions.
