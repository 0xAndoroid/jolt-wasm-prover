## 0. Fact base the tickets stand on

Stage absolutes @2^22 (canonical 88.44s × W2c shares): st0 36.1s (pairing absorb 23.7 / one-hot witness+tier1 11.2 / i128 1.2), st8 19.3s (combine_hints 6.4 / create_evaluation_proof≈fold_rows 6.4 / reduce+pairings+MSMs 6.5), st6b 13.5s, st5 7.1s, st1 4.4s, st2–4+6a+7 ≈ 8.1s, outside-prove 0.8s. @2^20 (33.19s): st0 15.9 (pairing 12.2), st8 8.9, st6b 3.6, st5 1.9, rest ≈ 2.9.

Rates: CPU-WASM 0.149 Gmul/s all-core (≈0.0149/core), GPU Tint 0.865–0.93 composed/packed, 0.40 raw-streaming. Browser orchestration: in-pass dispatch ~1 µs, submit 0.2 ms, **mapAsync readback 5–15 ms flat**. Pairs: 345,086 g2-setup pairs @2^22 (42 commit absorbs × 8192 + st8 tails ≈ 675 µs·core/pair ≈ 10K Fq-mul-eq); st8 also runs multi_pair_parallel 26 calls/16,382 pairs + g1_setup 0.6s. Warmup today: 1108 ms @6 pipelines (~285 ms per Fq point kernel).

**Post-W3a baseline (estimate, REPLACE with consolidation measurement):** W3a (dory Γ2 `init_cache` + batched-affine) removes G2 re-prep + conversions ≈ 25–35% of the 231.6 CPU-s absorb pool → whole-prove ≈ **81 ± 1.5s @2^22**, st0-pairing residue ≈ **16 ± 1.5s** (= Miller eval vs prepared coeffs + G1 conv + GT reduce), @2^20 ≈ 30.7s w/ pairing residue ≈ 8.5s.

Seam substrate (W2b, all tickets build on it, don't re-invent): `WebGpuEngine::run` phase jobs (1 submit ≤1 readback), `EngineState.slots` u64-handle residency, `webgpu_gate(kind, work)` + `WebGpuOptions { min_terms[_per_slot], handoff_len }`, generated WGSL off `MontgomeryConstants` w/ `FieldId::{Fr,Fq}`, slot-front pattern `WebGpuX { fallback: OptimizedX }`, `from_bound_tables` early-host-handoff (inc slot = the template, LIVE and parity-green), commit slot = tier-1 buckets on device / tier-2 absorb on CPU (T1's target), naga nextest + Tint wgsl-check + native byte_diff + browser gate-webgpu.mjs.

Hard rules (all tickets): ≤2 add-class EC bodies inlined per loop body, rolled loops (W2a wall — one step over = hour-long GPU zombie); dbl-class free to 8×; tiny-first probe (ec-probe.mjs pattern) for EVERY new kernel shape before full-size dispatch; micro-op/window/digit tables in **storage/uniform buffers, never module-scope const** (Tint per-thread-copy trap); packed Fe8 layouts on streamed operands (0.93 vs 0.40); timed passes only under ioreg GPU-util gate + bench lock; perf decisions on node-webgpu/Chrome only, never naga.

## T1 — Pairing lane (co-lead; biggest pool)

**Pool:** post-W3a st0 pairing residue ≈ 16s + st8 pairings ≈ 3.3s (multi_pair_parallel 1.4 + g2_setup-st8 1.3 + g1_setup 0.6) @2^22.

**Scope:** device multi-Miller behind Metal's hook seam; final exponentiation stays CPU (both donors shipped that way); GT partials tree-reduce on device, host finishes product + final exp. Hybrid CPU/GPU pair split (partition-invariant ⇒ byte-identical by construction).

**Integration (Metal's exact recipe, 4-file vendor diff):**
1. Vendor dory-pcs 0.4.0 → `vendor/dory-pcs` + root `[replace] "dory-pcs:0.4.0" = { path = "vendor/dory-pcs" }` (Metal Cargo.toml:196 precedent). Copy Metal's diff: `pairing_hook.rs` (`install_multi_pair_hook(fn(&[ArkG1],&[ArkG2]) -> Option<ArkGT>)` + guard, serves ALL THREE multi_pair entries), `reduce_and_fold.rs` `reduce_rounds_concurrent()` (concurrent per-message lanes only while hook installed; `JOLT_DORY_REDUCE_SEQUENTIAL` escape), and the **batch-normalize fix in `multi_pair_parallel`** (one batch inversion instead of per-point `into_affine` — free CPU win on wasm, ride it regardless of device path).
2. `webgpu/miller.rs` (new): hook impl — declines below gate/on failure (`None` → CPU path, fail-closed). Install per proof at first commit_witness / `webgpu()` bring-up; guard parked in `ProofSession` (Metal joint_opening pattern).
3. SRS-prepared detection: hook installer captures the process SRS `g2_vec` pointer range (jolt-dory exposes it); a call whose `qs` slice falls inside uses the **prepared path** at that offset; anything else takes the **computed path**. The flattened prepared-coeff table (Metal `flatten_prepared_coeffs`, step-major, ~16.9 KB/row ≈ 88 coeffs × 6 Fq) uploads ONCE per process off W3a's CPU cache: 8192 rows ≈ 138 MB device-resident — fine in the 4 GiB budget, and it serves all 42 absorbs + st8 SRS tails.

**Kernel inventory (two dispatch shapes — June's own tuning says which):**
- **Mega-batch (>512 pairs; the 8192-pair absorbs):** June's per-thread multi-dispatch pipeline (`pairing.rs::encode_miller_prepared/_computed`): ate loop unrolled into ~300 small dispatches in ONE submit (f_sqr_a/b, f_apply_a/b per step; split a/b kernels = lean by construction), per-pair state in storage buffers (f 96 u32 + scratch 144 u32/pair ≈ 1 KB/pair). Traffic @8192 pairs ≈ 2.4 GB/call at 90 GB/s ≈ 27 ms — bandwidth-fine; ALU ≈ 4.2K mul/pair. Dispatch overhead ~300 × 1 µs ≈ 0.3 ms.
- **Coop micro-op (≤512 pairs; st8 tails, computed multipairs):** June `coop.rs` + `coop_pairing.wgsl` — 32-lane WG per pair, CPU-built Fq2 micro-op stream (12 op codes, 56-slot wg file 3.5 KB, hazard-checked groups ≤32), whole loop one dispatch. **Verified compliant: 4 fq2_mul sites total (one per op-class branch), no inlined EC add-class bodies.** Ops/schedule in a storage buffer (already is — keep it).
- `COOP_MAX_PAIRS = 512` boundary is June-measured (coop ≈ ⅓ lane utilization above); keep as tunable, A/B at the 8192-pair shape once: per-thread vs 2-pairs-per-thread (Metal MILLER_SEG_PAIRS=2 won on Metal at 6.6 µs/pair vs 12.2 @8).
- Both paths end in a device GT tree-reduce to ≤64 partials → one small readback/call (never 8192 × 576 B).
- Prepared+computed line paths both required: computed = G2 prep ladder on device (June computed schedule; +~3.5K mul/pair) for st8's fresh G2s.

**Host/device split:** host = G1 batch-normalize + upload (512 KB/call), schedule/coeff tables, GT final product, final exp, transcript. Device = Miller evaluation (+G2 prep on computed path), GT tree-reduce. **Hybrid knob:** `miller_cpu_fraction` in `WebGpuOptions` (+`JOLT_WEBGPU_MILLER_CPU_FRACTION` native) — hook splits the pair range, CPU shard via rayon inside the hook, GT product merges. Metal default 0.5 (their sweep: 0→3.25s, 0.5→2.82, 1→4.78 st0 @2^22), M5 found 0.15; our CPU is 3.9× WASM-taxed ⇒ **expect optimum 0.05–0.2, default 0.1, sweep at bench time**.

**Files:** `vendor/dory-pcs/*` (new, owns), root `Cargo.toml` [replace], `webgpu/miller.rs` (new), `wgsl.rs` (+fq6/fq12 towers off P1's fq2 layer, +miller kernels — June `fq12.wgsl`/`pairing_fq12.wgsl` ports; append-only), `context.rs` (pipeline table append), `mod.rs` (install + options field), jolt-dory (expose SRS range; ~5 lines).

**Parity gates:** naga KATs — fq2/fq6/fq12 towers, single-pair Miller vs `Bn254::multi_miller_loop`, multi-pair partition invariance, prepared≡computed on same pair; Tint vectors for each; native byte_diff arm-on-forced (both paths forced via min_terms=1 + a forced-coop env) on sha2 2^13 + sha2_chain 2^19; browser gate @2^16; hybrid fraction ∈ {0, 0.5, 1} byte-identical.

**Acceptance @consolidated baseline:** device Miller ≤20 µs/pair browser-e2e (3× Metal's 6.63 native); st0 wall ≤ **18s @2^22** (from ~29 post-W3a) and ≤ **7s @2^20**; whole-prove −11s or better vs post-W3a; st8 pairing spans −2s; proof bytes identical; both-compiler gates green. Kill: µs/pair >40 after occupancy/shape sweep → keep pairings CPU, close lane (architecture doc W4 criterion, scaled).

**Effort:** 3–4 days fable-max. Risks: Fq12 tower register pressure (live state ~24–30 Fq on per-thread path — June PROVED it in-browser, but probe tiny-first); 138 MB coeff table + 4 GB wasm heap + Chrome co-residency (ledger it); pipeline count +~8 (~2.3s warmup add — outside timed windows, watch).

## T2 — Fold/sumcheck front (core lane; the 2× gate)

**Pool:** st5 7.1s + st6b 13.5s = 20.6s @2^22 (T-linear — 23.3% and growing; 2× whole-prove REQUIRES this lane, W2c D3).

**Re-scope vs the W2c-era sketch (donor says so):** Metal's proven st5 slot is NOT a round-loop port — device-worthy st5 mass = **O(T) phase-boundary passes** (16 phases × 3 passes: condensation, fused RAF scan, per-table suffix scan) + **adopted dense cycle rounds**; st6b = **LazyRa driver** (lazy gather rounds w1/2/4 off packed rows + `jk_ra_materialize` third-bind + dense rounds). One-shot O(T) scans don't fight the browser readback floor at all (1 readback/phase); only the dense-round ladders are round-serial and they ride the LIVE inc template + handoff.

**Split into two parallel-safe sub-lanes (disjoint files):**
- **T2a — st6b LazyRa (13.5s pool):** one device driver (port of Metal `slots/ra_lazy.rs`, 1461 lines) serving FOUR consumers — InstrRaVirt 42% + Booleanity 28% + BytecodeReadRafCycle 13% + RamRaVirt 8% = 91% of st6b (all four use trunk `optimized/lazy_ra.rs::LazyFoldedRa` already). Kernels: `ra_lazy_gather_w{1,2,4}` (gather branch-table pairs off packed rows + lane reduce; pure Fr, no EC), `ra_materialize` (dense gather at cycles/8 into flat device ping-pong), dense rounds = inc-template fused fold+eval with per-consumer summand. Host keeps binds, Gruen factor, claim assembly (Metal's parity recipe). Fallback = decline pre-round; `ensure_host` reclaims live tables at the shrunken length.
- **T2b — st5 PhaseScanner (7.1s pool):** port of Metal `slots/instruction_read_raf.rs` (1182 lines) + the optimized-kernel seam: scanner installed at prepare; per phase ONE job = 4 dispatches (fused condense+RAF scan, reduce, suffix scan, reduce) + 1 readback; at the address→cycle boundary adopt cycle tables into device ping-pong, cycle rounds = fused fold+eval. **Port the raw-space trick verbatim: `u·scalar` cells accumulate RAW on device + one value-space ×R on host = byte-identical to the CPU accumulator** — this is the parity linchpin. Decline/failure ⇒ `ScanOutcome::Corrupt` ⇒ kernel rebuilds u_evals and finishes on CPU.

**Trunk-port warning (the main cost):** trunk `optimized/` has ZERO device seams; Metal's seams are diffs against OLDER kernels (instruction_read_raf diverged 932 lines, lazy_ra 286, booleanity 244). **Re-derive the seam hooks against the trunk kernels; do not copy Metal files.** Structure is stable (same 8-variable prefix-suffix phases, same LazyFoldedRa) — the hooks transplant, the surrounding code doesn't.

**Residency & thresholds:** packed trace rows upload once via P2 handle (~0.5 GiB @2^22), shared by T2a gathers + T2b scans; ping-pong tables device-resident across rounds (inc pattern); ZERO per-round table readbacks. Browser handoff economics: per device round ≈ submit 0.2 ms + readback 5–15 ms + L/rate; CPU round ≈ c·L/0.149G ⇒ break-even **c·L ≈ 2.4 M mul-eq** (readback mid 10 ms). `DEFAULT_HANDOFF_LEN = 2^12` is native-shaped — browser sweep per slot over **2^14–2^19** (light folds c≈4 ⇒ ~2^19; heavy product-grid rounds c≈20–50 ⇒ 2^15–2^16). **Step 0 of this ticket (~30 min): measure the LIVE inc slot's browser per-round latency @2^16–2^22 — W2b never timed it; it calibrates every threshold in this lane.**

**Files:** T2a: `webgpu/slots/ra_lazy.rs` (new), `optimized/lazy_ra.rs` + install points in `optimized/{booleanity, instruction_ra_virtualization, bytecode_read_raf, ram_ra_virtualization}.rs`, `wgsl.rs`/`context.rs`/`mod.rs` appends. T2b: `webgpu/slots/instruction_read_raf.rs` (new), `optimized/instruction_read_raf.rs` seam, same shared appends. No jolt-dory, no vendor.

**Parity gates:** per-kernel naga KATs vs host mirrors (gather/scan/fold; raw-space ×R equivalence test); Tint vectors; lockstep round parity vs optimized kernels (harness `run_lockstep`, inc-test pattern) per consumer; native byte_diff forced (min_terms=1 × handoff ∈ {64, default, ∞}); browser gate @2^16; four-consumer forced-env sweep.

**Acceptance:** st5+st6b ≤ **9s @2^22** (−11.6s vs baseline; = covered 91%/86% at ~3× + readback taxes), ≤ **2.6s @2^20**; bytes identical everywhere; no per-round table readbacks in traces (aggregate-trace.mjs check). Kill: first consumer lands net-negative @2^22 after threshold sweep → stop the front, keep EC lanes (architecture W5 criterion).

**Effort:** T2a 2.5–3 days, T2b 2–2.5 days (parallel workers OK; if one worker, T2a first — bigger pool). Risks: trunk-kernel drift makes seam re-derivation the long pole; gather kernels are random-access (bandwidth-shape unknown — probe early against the 0.40 raw floor; Fe8-pack the hot tables).

## T3 — st8 opening lane

**Pool (post-T1 attribution):** combine_hints 6.4 + fold_rows/create_eval 6.4 + reduce folds 2.25 (apply_first 1.44 + apply_second 0.81) + G2 MSM 0.6 ≈ **15.7s @2^22** (pairing spans belong to T1).

**Scope — three device pieces, all donor-complete:**
1. **combine_hints** (Metal `hint_combine.rs`, 331 lines): jolt-dory `hint_hook.rs` port (`install_combine_hints_hook` + guard, parked in ProofSession by the joint-opening slot). Kernel `hint_combine_rows`: thread per output row, ONE high-to-low double-and-add across the row's ~40 hints sharing the γ-power scalars (bit branches warp-uniform; ~254 dbl amortize over the row), hints host-sorted by row count desc (prefix-structured raggedness, one uniform break), host batch-normalize + (0,0) identity sentinel, canonical scalar limbs in storage buffer. Reuses the commit lane's guarded madd body — ONE add-class inline ✓. ~164K plain scalar-muls @2^22 ≈ 0.38 Gmul ⇒ ~0.5s device vs 6.4s CPU. (Fallback if lane slips: the W2c CPU GLV fix ≈ 3.5× — but the device design is strictly better and donor-complete.)
2. **fold_rows FoldEngine** (Metal `slots/joint_opening.rs`, 852 lines): the batch opening's ~42 per-constituent full-T `fold_rows` passes collapse to ONE device pass — first call computes every trace constituent's fold (one dispatch per column family, one submit), caches per-slot results keyed on exact `(left, σ)`, revalidates/recomputes on mismatch. **Cycle-major placements only** (grid index = cycle + address·2^log_T, σ ≤ log_T ⇒ thread-per-output-column owns its accumulators, no atomics); address-major/advice → optimized twin wholesale. Fr-sum regrouping is exact ⇒ byte-identical; i128 increments lift through the same canonical-Montgomery conversion both sides. Columns come from the P2 packed-rows handle when present, self-upload otherwise (state the fallback in code). 6.4s → ~1.7s (fold mass at 0.4–0.93 + one upload).
3. **Dory reduce folds** (Metal `dory_folds.rs`, 641 lines): jolt-dory `routines_hook.rs` port (`install_routine_hooks(RoutineHooks{ g1_scalar_mul_add, g2_scalar_mul_add, g2_fixed_base_mul })`; `JoltG{1,2}Routines` check the hook first). Kernels: thread-per-element double-and-add ladder, ONE shared scalar (uniform bit branches), mixed madd on host-batch-normalized affine inputs, (0,0) sentinel, results Jacobian (consumers normalize ⇒ bytes unchanged). G2 variant on P1's fq2 layer (live state ~10–12 Fq — W2a curves were flat to 9; tiny-first probe). **CANONICAL-scalar upload landmine (cuda dory_reduce.rs:38–41 note): ladder bit-tests need canonical integer limbs, not Montgomery.** v1/v2 residency ping-pong on device across rounds where the routines allow (upload once at reduce start, readback at the ≤`handoff` tail — CUDA's 256-term recipe); per-round message readbacks are the small evals only. 2.25s → ~0.7s. G2 MSM (39 calls/32,764 pts) rides `msm` through the same hook only if free; else stays CPU (0.6s, below gate).

**Files:** jolt-dory `hint_hook.rs` + `routines_hook.rs` (new) + `lib.rs` (+2 module lines) + `routines.rs` (hook checks); `webgpu/{hint_combine.rs, dory_folds.rs}` + `webgpu/slots/joint_opening.rs` (new); `optimized/opening.rs` (FoldEngine seam — re-derive against trunk, same warning as T2); shared appends (`wgsl.rs`, `context.rs`, `mod.rs`). **Does NOT touch vendor/dory-pcs** (T1 owns it); benefits from T1's `reduce_rounds_concurrent` when both land.

**Parity gates:** naga KATs — hint-combine vs host combination on ragged fixtures, fold_rows vs optimized on cycle-major grids incl. i128 columns, G1/G2 scalar-mul-add vs ark (identity/sentinel paths); Tint vectors; native byte_diff forced; browser gate; hook-installed vs not byte-identical.

**Acceptance:** st8 wall ≤ **8s @2^22** with T3 alone (from 19.3), ≤ **5.5s** with T1 landed too; ≤ **3s @2^20** (with T1); bytes identical. Kill: st8 delta <15% of whole-prove → descope to combine_hints only (architecture W3 criterion).

**Effort:** 3–3.5 days. Dependency: P1 (fq2 layer) required for the G2 fold kernel; P2 optional (self-upload fallback); T2 NOT required.

## The arithmetic to 2.05× (and the 2.5× stretch)

@2^22, mid estimates (± ranges are the lanes' honest spread):

| step | Δs | wall after |
|---|---|---|
| clean baseline | — | 88.44 |
| W3a cache fix (P0-measured) | −6…8 | ~81.4 |
| T1 pairing (16+3.3 → ~4) | −15 ± 3 | ~66.4 |
| T2 fold front (20.6 → ~8) | −13 ± 3 | ~53.4 |
| T3 st8 (15.7 → ~4.7) | −11 ± 2 | ~42.4 |
| T4 tier-1 | −3…5 | **~38.5** |

**2.05× (43.1s) is reached by W3a+T1+T2+T3 at MID estimates — T4 is margin, not requirement.** Any ONE core lane landing at its low edge is absorbed by the others' mid. @2^20 the same set lands ~14–16s ≈ 2.1–2.3× (smaller calls, more below-gate CPU residue).

**Stretch 2.5× (35.4s):** needs T4 PLUS two of the three core lanes at their high edge (T1 −17: fraction sweep + coop A/B; T2 −15: packed gathers at 0.93 not 0.40; T3 −12: FoldEngine + resident reduce both at packed rates). Absolute ceiling of this ticket set ≈ **29–30s (untouched st1–4/6a/7 + outside ≈ 12.5s, plus lane floors ~17s) ≈ 3.0×** — anything past 2.5× requires the small stages (st1–4 ≈ 11s, Metal two-phase slot set = W5-era material) or X21 landing big.

Report cadence: each lane appends its Worker-log section with measured stage deltas vs the P0 baseline; the consolidated post-W3 bench (same gates) is the user-facing beat.
